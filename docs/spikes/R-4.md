# Spike R-4: 3D frame time at 30k elements

Research in an isolated worktree; nothing applied yet. Patch: `docs/spikes/r4-settle.patch`.

R-4 is mostly a frame-count problem. A filter click at 30k drew two to four 3D frames instead of one, and in headless Chromium each software-WebGL frame blocks the page's main thread for 0.3-0.9 s. A minimal patch that waits until every model shows its changes and then draws once brings the complete frame (last changed frame drawn) at 30k under 500 ms: 298-349 ms median, down from 244-1,081 ms. The time until the pixels are actually on screen in headless is still 0.7-1.1 s at 30k, because one software-WebGL frame alone costs 550-700 ms; nothing in the app can fix that short of drawing fewer triangles.

`node scripts/check.mjs` is green with the patch. All e2e and acceptance specs pass on both projects (view-3d + smoke 18, filter/layout 30, table/grouping 42, acceptance 8). The perf specs `test/perf/view-3d.spec.mjs` and `test/perf/table.spec.mjs` pass in the file project. Medians of 5 below come from A/B runs: original and patched page in two tabs of one browser, runs interleaved. Load average was 3-4.5 during the final runs; other agents' test suites were running in parallel, and some exploratory runs were at load 6-10. "done" is the first animation frame after the last changed frame, which is when the pixels are actually there in headless.

## Where the time goes
- **The frame blocks the main thread.** A trace of one click at 10k shows the page's commit reading the WebGL canvas back synchronously (`GLES2::ReadPixels`, 413 ms and 284 ms). The GPU process spends the same time on the WebGL work, so the main thread is blocked for the whole software-WebGL frame. The Fragments worker was busy only 49-84 ms; the engine calls took 13-27 ms each.
- **Partial first frame.** The five models' tile updates arrive 50-300 ms apart, and Fragments only passes them on with its own ~100 ms delayed refresh. The current code draws as soon as the first model changes. That frame blocks everything, so the remaining models' changes, and sometimes even the remaining `highlight` calls (786 ms and 1,572 ms observed), wait behind it. A second (third, fourth) frame follows.
- **Uncheck in ghost mode changes tiles twice.** After `resetHighlight`, a model's tiles change in two steps 20-90 ms apart.
- **The frame itself is geometry-bound, not pixel-bound** (render plus a 1-pixel `readPixels` to force completion):

| Set | Triangles / draw calls | Antialias on | Antialias off | Pixel ratio 0.75 / 0.5 | Hide mode |
|---|---|---|---|---|---|
| 10k | 163k / 378 | 241 ms | 219 ms | no gain (281 / 285 ms) | 159 ms |
| 30k | 380k / 603 | 579-687 ms | 593-648 ms | no gain | 348-388 ms |

- **Ruled out as levers:**
  - An opaque ghost material is not cheaper (708 ms) and visibly loses the X-ray look.
  - Fragments `graphicsQuality` 1 or 2 doubles the triangles (676-714 ms at 10k); 0, the default, is already the cheapest.
  - `gl.finish()` returns in 2 ms and does not wait for the frame, so it cannot be used to time it.

## Risks of the patch
- **It relies on Fragments internals that are already in use** (`tiles` signature, `onViewUpdated`). New is the assumption that a model that received calls changes its tiles. If it does not, drawing waits at most 300 ms after the last call (`SETTLE_MS`).
- **Extra refreshes.** While models settle (at most 300 ms), all models refresh about every 16 ms plus the refresh time, which adds worker load. `applied` did not get worse.
- **First change appears later.** The first visible frame comes up to one refresh round later. On a real GPU that is roughly 20-100 ms; the complete frame there is earlier or the same.
- **Camera moves are unaffected** (they draw directly), and model removal clears its pending state.
- **`whenIdle` now also waits for settling**, so the tests cannot miss a later frame.
- **Ghost uncheck at 30k can still get a second frame** under load, when the second tile change arrives after the 300 ms cap (1 of 5 runs in the final A/B).
- **Not covered:** the selection and IfcSpace-visibility calls, which normally touch one model.

## Is headless software WebGL representative?
For the 3D frame, no: it is a pessimistic worst case. SwiftShader takes about 1.5 µs per triangle, and the headless compositor reads the canvas back synchronously, so every frame freezes the main thread. On a real GPU, 380k triangles and 603 draw calls cost a few ms of GPU time. The three.js work per frame measured 2-11 ms of CPU, and there is no readback. A click should then complete in roughly applied + tile latency + one frame, about 150-300 ms at 30k, and partial frames are harmless. That is an estimate; I did not measure on a GPU.

Headless is representative of a PC without hardware acceleration (VMs, remote desktop, blocked GPU). There one frame at 30k costs 0.6-0.9 s, so pixels on screen cannot be ≤ 500 ms without drawing less. I'm not certain of the status of Chrome's automatic SwiftShader fallback for WebGL: it has been deprecated, and on such machines WebGL may not be available at all.

**Decision to confirm (for TASK-010; this is a business rule, so I did not decide it):** at 30k, does NFR-001 mean "last changed frame drawn" (met with the patch: 298-349 ms median) or "pixels on screen" (not reachable in software WebGL: 0.7-1.1 s, about 1 s worst case)? The most conservative reading is "pixels on screen", which in this environment would mean NFR-001 is met only on a GPU, or needs a recorded deviation for software rendering.
